# Mercenaries Recompiled – Android port

**Status: all game sources are ported and the whole source set compiles under Android-style rules on a host
machine; it has not been built with the Android NDK or run on a device.** The environment this was written
in had no NDK, no network and no disc image, so no game frame has ever been rendered and performance is unknown.

## What "ported" means here
Every file the Windows build compiles now builds for Android, from the *same* sources (`#if XBOX_ANDROID`
branches keep the Windows build unchanged). `tests/check_android_sources.py` simulates the CMake build:
it reads the source lists out of `CMakeLists.txt`, compiles all 38 toolkit + 24 game sources with the same
include path and definitions (clang-strict: implicit function declarations are errors), and classifies every
unresolved symbol as libc / Android glue / recompiler output. It currently reports none unaccounted for.

| Area | Result |
|---|---|
| `main.c` (startup) | Builds as `mercenaries_android_main()`; token window handle, same D3D8 device parameters, Resolution option → back-buffer size, no-op x86 debug-register watchpoints, SIGSEGV-based crash report, 64 MB game-thread stack (the Windows build links with 64 MB) |
| `recomp_manual.c` (19,700 lines of game logic) | Compiles unmodified apart from fencing off two x86 host-register dumps |
| Controls / prompts | Gamepad binding logic kept; raw-mouse/`WM_*` code is Windows-only and inert (input = gamepad + touch overlay) |
| Dev overlay | Rewritten with a built-in pixel font (no GDI); set `MERCENARIES_FPS_OVERLAY=1` for FPS/frame-time graph |
| Dev menu | Win32 panel has no phone equivalent; same API kept (catalogs, request queues, developer.ini switches) |
| Plugins / mod saves / mod selector | Desktop-only (DLLs, separate selector app); behave exactly as "no mod selected" |
| PS2 upgrade assets, Lua scripts, catalogs, shader warm-up list | Generated by `gen_game_headers.py` (byte-exact vs the CMake scripts; Lua round-trip verified) |
| Win32 API surface | ~35 missing functions implemented in `compat/winapi_extra.c` incl. real INI files (`GetPrivateProfile*`), secure string functions, SHA-256 behind the BCrypt shim |

### Bugs found and fixed along the way (would have broken the Android build or game)
- `RtlInitUnicodeString` used 32-bit `wcslen` on 16-bit Xbox `WCHAR` strings (wrong length) – fixed in the toolkit.
- No case-insensitive file lookup: the game requests `D:\Media\Intro.XMV` while Android is case-sensitive. The importer
  now writes lower-case names and `kernel_path.c` folds requests the same way (tested end to end).
- Default thread stacks were 1 MB vs the Windows build's 64 MB reserve.
- Undeclared functions that MSVC tolerates and the NDK's clang rejects.
- `xbox_prepare_empty_cache_volume` had no POSIX implementation.

## Renderer: Direct3D 11 on OpenGL ES 3.0
`nv2a_pgraph_d3d11.c` + `d3d8_*.c` run **unmodified** on `cpp/d3d11_gles/` (a D3D11/DXGI/D3DCompile implementation
over GLES 3.0 with an HLSL→GLSL ES translator). Verified on Mesa GLES 3.2: all embedded shaders translate and
compile; the project's NV2A vertex-shader and register-combiner generators, fuzzed, produce 0 rejected shaders
(540 vertex / 1000 combiner); 28 pixel-level checks through the D3D11 API. Known gaps (GLES 3.0 limits): geometry
shaders (scaled lines fall back to thin lines), per-render-target blend state, wireframe, depth-clip control,
stencil-texture sampling, BC read-back, MSAA.

## Verified by `tests/run-host-tests.sh` (Linux; GPU tests use Mesa llvmpipe)
XDVDFS importer · AArch64 MMIO decoder · `mmap` guest-memory layout · Win32 compat (INI, strings, paths, atomics) ·
SHA-256 (NIST vectors) · case folding · whole-source-set check · HLSL translator · D3D11-on-GLES · shader generators.

## Not done / not verifiable here
1. **Game code.** Generated from *your* disc by `tools/recomp` on a PC (default location `ports/mercenaries/src/recomp/gen`,
   or `-PmercGenDir=`). Without it the app builds as an importer + status shell.
2. **First NDK build.** CMake is untested against a real NDK. Expect to iterate on compile/link errors
   (the host check covers undeclared functions, missing files and unresolved symbols, not NDK-header differences).
3. **Run-time behaviour on a phone**: speed (lifted x86 + NV2A emulation), shader-compile hitching, thermal limits.
4. **DSP56300 audio**: the prebuilt library is MSVC-only; rebuild `third_party/dsp56300` for `aarch64-linux-android` or audio runs without it.
5. **Mods, plugins, dev menu panel, keyboard/mouse** are not available on Android.

## Building
Run `tools/recomp` on a PC with your disc image, open this folder in Android Studio (NDK 26.3), then
`./gradlew assembleDebug`. arm64-v8a only. Needs Python 3 on the build machine (header generation).
Install, tap *Import*, choose your `.iso`, tap *Play*. Logs: `adb logcat -s MercRecomp MercGame d3d11gles`.

## Touch controls
The two circular pads are independent analog sticks: left for movement and right for
camera/aim. Drag from within a pad; the knob follows your finger and stays held even
if you move outside the circle. Release it to recenter. Face buttons and both sticks
can be used at the same time, and physical controllers remain supported.

## Android performance diagnostics
The shared game log includes `[perf]` samples every ten seconds while rendering, with observed FPS and
average `eglSwapBuffers` wait time and game-thread CPU time as a percentage of one core. Long background/stalled gaps reset the sample. These numbers alone
do not distinguish CPU from GPU bottlenecks. `[perf-mmio]` reports handled NV2A
fault-driven register reads and writes per interval; `put_kicks` is the subset
of writes to the GPU command-buffer PUT register. It excludes other devices,
direct accesses and failed decodes. Counts do not measure CPU time, and the
three counters are sampled independently; a background gap resets the baseline.
These diagnostics do not themselves improve FPS. `[perf-gles]` reports per-interval draw,
buffer map/unmap and readback counts, sampled CPU-side call times (one in 64 calls),
the number of full draw-state applications (`state_applies`), and the current shader-program cache size.
Transient vertex-ring map/unmap calls
are reported separately as `ring_maps` and `ring_unmaps`. These samples can miss occasional spikes
and do not measure GPU execution time. `[perf-gles-draw]` separates sampled
CPU time spent preparing a draw from the driver draw call. `[perf-gles-prepare]`
breaks preparation into program lookup/creation, framebuffer and state setup,
resource binding, and vertex setup. `[perf-gles-fbstate]` further separates
framebuffer binding from render-state application. `[perf-gles-workload]` counts
issued array/indexed draws, submitted vertex or index references, draw sizes
(disjoint ranges), renderer draw-FBO rebinds and attachment changes; clears and
blits are not counted as draw-FBO rebinds; attachment updates include clears.
`[perf-gles-buffer]` breaks general buffer maps, discard maps, failures,
nominal mapped bytes, sampled map/unmap CPU times, and UpdateSubresource calls
and bytes into mutually exclusive constant, vertex, index and other bind-flag
categories. `[perf-gles-constant-size]` shows the first six constant-buffer
sizes seen, with any additional sizes counted in `[perf-gles-constant-other]`;
size can help identify a buffer but is not a unique call-site ID. Persistent ring copies and their fallback ring maps are separate;
bytes count the requested full buffer size, not the bytes actually changed.
`[perf-gles-target]` reports the first six render-target size/depth combinations
seen in each interval and issued draws and vertices; overflow draws are counted
in `[perf-gles-target-other]`. These are not terrain/scenery labels and do not
measure GPU execution. `[world-scene-sample]` is a periodic read-only RedScene
query snapshot, including the known terrain entry, known model-vtable entries,
and spheres wholly beyond 260 radial units; none is a safe culling decision.
`[world-projection]` distinguishes the authored camera field from the actual
argument sent to SetPerspective when the eligible camera path runs;
`[world-projection-bypass]` reports unmatched far arguments on that camera.
Fog cutoff
and draw origins remain unverified.
`[perf-gles-small]` separates small draws (up to 16 vertices/indices) by
vertex-ID-only versus attribute input and by primitive topology. Vertex-ID-only
draws can include internal resolve passes; the category is not an exact origin label.
`[perf-nv2a-small]` counts guest draw submission paths and small NV2A triangle
strips, how many have an enabled texture stage, and non-contiguous DRAW_ARRAYS
splits (all primitive modes and strips respectively). These are diagnostic
counts, not proof that a particular pair can be safely merged. Each timing is sampled independently, so their
averages need not sum exactly to the preparation average. These wall times can
include driver waits or backpressure; none is a GPU timer. Android normally collects GLES errors at
presentation instead of after every hot draw/upload. Set `D3DGL_DEBUG=1` for
per-operation GL error checks and attribution when investigating graphics.

Detailed game preview telemetry is disabled unless developer logging is enabled via
`config/developer.ini` (`[Developer] logging=1`) or the `MERCENARIES_DEVELOPER_LOGGING`
environment variable. Lifecycle, performance and crash traces remain enabled.

The thread-sampling watchdog is disabled by default to avoid interrupting gameplay. For a hang investigation,
create a file named `watchdog.enable` in the app's cache directory before starting the game. Remove it to
turn sampling off. Crash reporting remains enabled without the watchdog.

### Texture and streaming memory
GLES uploads already-native texture formats directly, using GLES 3 row length
for representable padded rows; formats requiring conversion retain the CPU
conversion path. Large BC1/2/3 textures are decoded in block-row chunks (about
1 MiB of temporary RGBA data at a time) instead of allocating a full decoded
image. Compressed staging copies address block rows, not pixel rows. Small
indexed guest draws use a bounded 2 KiB scratch buffer, with heap fallback for
larger draws. These changes preserve the content and do not alter game draw
distance. They reduce copying and temporary memory, but do not reduce the
number of scene draws or prove an FPS gain.

Android uses the POSIX file path and the operating system's buffered file
cache; the separate Windows-only guest read-ahead cache does not apply to it.
These texture chunks are upload/decode chunks, not a change to the game's
world-streaming grid or asset lifetime.

### Android world distance trial
The normal world-camera far plane and eligible scenery distances are capped at
260 game units, and the shared world streaming grid uses 320. Shorter authored
distances are not increased. The 60-unit difference is relative to the camera's
axial far-plane value and scenery threshold; wide-FOV corners, large objects and
fast movement can still reach outside the grid. Other camera types, terrain's
own budget and NPC distance settings are not directly changed.

This experiment is not calibrated to the fog cutoff and may cause pop-in or
missing objects. Test fast vehicles and missions on a device. A `[world-streaming]`
line at world initialization reports the values. The grid patch requires the
game's generated sources to be regenerated when building.

### CPU affinity and thermal diagnostics
The game-thread tuning helper is compiled into `android_game.c` for game builds.
After 15 seconds it attempts to select the highest-capacity cores, intersected
with the game thread's existing allowed CPU mask. It falls back to maximum CPU
frequency only when capacity information is unavailable or does not show a
split. If no reliable split is visible or no selected core is allowed, affinity
is left unchanged. The priority request can be denied by Android; `[cpu]`
records the result and errno. Every ten seconds the helper reports the last
observed game-thread CPU, available core frequencies, and the hottest readable
thermal zone; unavailable sysfs information is reported as `n/a`. The hottest
zone is not necessarily the CPU and these measurements alone cannot prove why
a frame stalls. Pinning may hurt performance, power or thermals. Threads created
later by the game thread may inherit its affinity.

To override, create `cpu_affinity.txt` in the app's cache directory before
launch with a hexadecimal mask (for example `c0`). Write `0` to disable both
affinity and the priority request while retaining telemetry. This file is read
once after the 15-second delay; restart to apply changes. Core numbering and
access to sysfs vary by device. `python3 CPUFIX/apply_cpu_tuning.py` reinstalls
the included helper idempotently; ordinary builds already include it.

### NV2A draw merging

The experimental draw merger is disabled and no startup marker or environment
variable can enable it. The renderer submits guest draws separately. The PFIFO
fast path for consecutive data words within one draw remains; it does not merge
separate draws.

`[perf-nv2a-adjacent]` is a read-only probe of the packet immediately after a
triangle-strip END, grouped by the current draw source. `boundary` means less
than two words were available before PUT/DMA end; `barrier` means the next
packet was not a same-subchannel BEGIN; `begin_other` means BEGIN used a
non-strip mode. The `strip_*` fields describe only the first packet after a
same-subchannel strip BEGIN. They do not establish a complete draw, unchanged
state, texture safety or permission to merge. Counts are per ten-second
workload interval and do not change PFIFO execution.

The Android `[world-visibility]` sample observes the retail RedScene query list
once every ten seconds. `behind_candidate` means a finite bounding sphere lies
wholly behind the camera plane, not that it is safe to skip: objects may be
needed for shadows or other passes. It never removes objects (`culled=0`). The
fog cutoff remains unknown; these samples do not change streaming, gameplay or
draw submission. The retail query's use of the negative camera axis is based
on its instructions at 0x002034A0; camera/pass and bounds semantics still need
device validation before using the observation to affect rendering.

`[world-fog]` counts NV2A draws with fog enabled/disabled and enabled draws
using a programmable vertex shader; the two reported mode values are the last
observed enabled-draw state in the interval, not a measured cutoff. Programmable
shaders can compute their own `oFog`, and fog can vary by scene and material.
Neither that state nor the camera far plane alone proves a safe distance at
which to omit geometry, depth, shadows, or reflections.

### Draw limit

The experimental 25,000-draw limit was removed. Game draw calls are not
dropped by a draw-count limit, and no cache marker is required.

The periodic `[cpu]` line also includes battery temperature in Celsius (when
Android exposes `/sys/class/power_supply/battery/temp`), and CPU6's governor,
current scaling maximum and hardware maximum in MHz. `n/a` means unavailable
or invalid; CPU6 may not be a big core on other devices. Battery temperature is
not CPU temperature. A policy limit below the hardware maximum indicates a
configured cap at that instant, not necessarily thermal throttling; sampled
frequencies and policy values do not measure sustained clock speeds.

On supported Android devices the game requests an Android performance-hint
session for the game thread. Its work-duration target follows the selected FPS
cap; uncapped uses a 60 FPS target, and unsupported devices keep the initial
30 FPS target. It reports frame work before swap, skipping long lifecycle gaps. This is a scheduler hint,
not a frame cap or guaranteed clock boost; Android may reject or ignore it.
`[cpu] Android performance hint session active/unavailable` reports session setup.

Android `DrawIndexedPrimitiveUP` can reuse transient vertex and index buffers
for supported indexed draws instead of creating two buffers each time. Buffer
wrap orphans old storage. Unsupported formats, primitive conversions, restart
indices, nonzero minimum vertices and oversized draws remain on the older path.
On Android, eligible NV2A programmable indexed draws are compacted from their
existing vertex snapshots and submitted through the indexed path when upload
bytes fall by at least 25%. Draw order stays unchanged; unsupported topologies,
sparse indices, inconsistent snapshots, fixed-function draws and failures keep
the expanded path. Small eligible draws now build their compact input during
the expansion pass, avoiding a second compaction pass while keeping the ordered
snapshot for diagnostics. CPU expansion still occurs; any FPS benefit needs
on-device validation.

The Android vertex and index rings can each reuse up to four recent,
byte-identical uploads of at most 128 bytes. Every draw still executes; none
are merged. Entries are invalidated on ring discard, upload failure, or
shutdown. `[perf-gles-workload]` reports `ring_vertex_reuses` and
`ring_index_reuses` per interval. Test FPS and graphics on-device, since a low
hit rate can make the cache overhead outweigh its benefit. Programmable vertex
shader constants also skip upload if guest writes return to the last uploaded
bytes before a draw; a failed map stays dirty for a later retry.

### Experimental persistent UP ring storage

The dedicated Android vertex and index UP rings try `GL_EXT_buffer_storage`
with a persistent coherent write mapping. When supported, each upload copies
into the mapping without a per-draw GL map/unmap. On ring wrap it rotates among
up to three lazily allocated buffer generations. A GPU fence is waited before a
previous generation is reused; allocation failure falls back to waiting on the
current generation. Waiting can stall and must be measured on-device. The two
4 MiB rings can together use up to 24 MiB of persistent buffer storage, plus
driver overhead. Set `D3DGL_NO_PERSISTENT_RING=1` before the game starts to
force the existing mutable map/unmap path. Initial allocation or capability
failure also uses that path. The fallback is not batched: draws currently consume their data
immediately, and delaying uploads requires a correctly ordered command stream.
The earlier per-draw `glBufferSubData` experiment performed poorly in a phone
log, so it has not been reinstated as a presumed batching optimization. Draws
are not merged. Look for `[gles-ring]` and `[perf-gles-persistent]` in the exported log;
compare graphics, FPS, upload counts and wrap wait time in matched scenes.

### NV2A vertex preparation

Inline array packets are copied into the inline buffer and submitted through
`submit_array_draw`; programmable draws normally pass their existing vertex
format to the host input layout rather than converting every component on the
CPU. Indexed element draws still expand guest vertices into a CPU snapshot.
Immediate draws capture all 16 input registers per vertex and also build a
pre-transformed fallback/diagnostic vertex; quads and line loops require ordered
expansion. Strips are not routinely converted to lists in these paths.

Immediate position/UV conversion now copies contiguous bit patterns, and quads
reuse the already-converted first and third vertices. Batched 16-bit element
packets unpack four words at a time using AArch64 NEON, with a scalar tail and
portable fallback. This is index unpacking, not a GPU vertex shader conversion.
On Android, `[perf-nv2a-vertices]` reports submitted input vertices by source;
`[perf-nv2a-convert]` reports call/item totals and sampled CPU durations for
indexed snapshot expansion, immediate fallback output, and 16-bit index unpack.
These timings omit other vertex work and are not GPU timings. The NEON path,
rendering correctness and performance still require phone validation.
